# Synora 0.2.4 — Core update policy migration

Candidate release. Package publication and native installation must be recorded
separately; source changes do not update already installed clients.

## Changes

- Ordinary Core discovery/qualification/publication runs on internal GitLab,
  independently per target. No personal Mac/Windows computer is a CI dependency.
- A new signed v2 catalog explicitly describes central Linux compatibility and
  mandatory native client activation checks. It does not claim native Mac/Windows
  UI qualification. The legacy v1 endpoint is preserved for older applications.
- Synora checks the signed site channel on startup (30 seconds) and every six
  hours, without waiting for a separate upstream GitHub discovery request.
- Exact hashes and full package inventories remain required. Version, isolated
  App Server initialization, settings and history APIs are probed on the local
  machine before an idle-only switch. Previous runtime/data are retained.
- Failed local activation leaves the previous Core selected and suppresses an
  automatic retry loop for that version. No model request or OS permission grant
  is generated by the activation probe.

## Qualification boundaries

Server tests use the real candidate Linux Core with controlled loopback Responses,
real command/result, streaming, cold resume and cancellation, plus provider/MCP
contract tests. They do not call public model/search services and are not a claim
that every external service, plugin, OS sandbox or GUI behavior is working.

Full native app audits retain all original gates in a separate GitLab lane.
macOS remains locally signed (not Apple notarized); Windows remains unsigned.
Bundled baseline remains Core 0.154.0 with 0.153.4 recovery until a separately
authorized candidate is downloaded and locally activated.

Initial source regression: 788 tests passed, zero failed/skipped, and eight atomic
deployment tests passed. Final package/native results are recorded after building.
